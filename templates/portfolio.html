GT Movies Store

An online report on GT Movies Store, a Django web app for browsing movies, reviewing them, and buying them. Who I am, what I built, how each screen answers a user story, and how I actually worked on it.

02GT Movies Store

GT Movies Store is a Django app for a movie storefront. You can browse the catalog, search it, and read reviews without an account. Sign up and you can write reviews, fill a cart, and check out into an order history.

Architecture

I split it into four Django apps instead of one big one. Each owns its own urls, views, templates, and models.

  • homeLanding page and about page. No models.
  • moviesThe Movie and Review models, the catalog, search, detail pages, and reviews.
  • cartThe session cart, plus the Order and Item models checkout writes to.
  • accountsSignup, login, logout, and order history on top of Django's User.

The data model is small. Movie has a name, price, description, and an uploaded image. Review points at both a movie and a user, so it always knows who wrote it. That's what makes the ownership checks possible later.

Checkout creates an Order for the user and one Item per movie. Each item copies the price and quantity at the time of purchase. That part matters. Because the price is copied instead of read through the foreign key, changing a movie's price later doesn't rewrite what someone already paid.

The cart lives in the session, not the database, as a map of movie id to quantity. So you can fill a cart before you have an account. Only purchase is behind @login_required, so you hit the login wall at checkout instead of at the door.

Screens and the user stories they answer

Screen Route What it does
Home / The front door. Store branding and a way into the catalog, so a first visit lands somewhere instead of on a bare list.
About /about Static page for "what is this store".
Movie list /movies/ "Browse all movies" and "search by name". The view reads a search query param and filters with a case insensitive name__icontains. No param means the full catalog, so one screen covers both stories and an empty search never dead ends.
Movie detail /movies/<id>/ "See the details" and "read the reviews". Shows the image, description, and price, pulls every review for that movie, and holds the add to cart form and the review box.
Sign up /accounts/signup "Make an account". Wraps Django's UserCreationForm in a subclass that drops the default help text and adds Bootstrap classes. A custom error list renders validation errors as styled alerts instead of a raw list.
Login and logout /accounts/login/ "Log in and out". Authenticates against Django's backend. A failure re renders the form with one generic message, so a wrong password doesn't tell you whether the username exists.
Cart /cart/ "Add movies with a quantity and see the total". Lists what's in the session cart, totals it in a calculate_cart_total helper, and has a clear button. A custom filter, get_quantity, pulls each quantity out of the session dict in the template, since Django templates can't subscript a dict by a variable key. That filter is what keeps the logic out of the view.
Purchase confirmation /cart/purchase/ "Check out". Saves the order and its items, empties the session cart so a refresh can't order twice, and shows the new order id.
Order history /accounts/orders/ "See my past orders". Reads orders off the logged in user through the reverse relation, so it's scoped to that account automatically instead of by a filter I could forget.
Create, edit, delete review /movies/<id>/review/... "Write a review, edit or delete my own". All four review views are behind @login_required. Edit checks that the review's author is the current user and redirects away if not. Delete scopes its lookup to user=request.user, so someone else's review 404s instead of getting deleted. Empty comments get rejected on create and edit.
Report review /movies/<id>/review/<id>/report/ Extra feature, not one of the required stories. A logged in user can take down a review they think is inappropriate without waiting on an admin.
Admin /admin/ Django admin with the models registered, so staff can manage the catalog. Poster uploads land in media/movie_images/ and get served through a MEDIA_URL route in development.

Interface

Every page extends one base.html holding the navbar and footer, so a new page gets the shared layout for free. The navbar knows if you're logged in. It swaps Login and Sign Up for Orders and a logout link with your username on it, so you can always tell which account you're in. Layout is Bootstrap 5 over a small custom stylesheet, and the navbar collapses so the store still works on a phone.

03Process

I built it one app at a time and treated each user story as one piece of work. Instead of designing the whole schema first and wiring views to it after, I took one feature all the way through (model, url, view, template) and checked it in the browser before starting the next.

The order followed what depended on what. home first, to get a skeleton rendering. movies next, since everything else points at a movie. accounts after that, because reviews and orders both need a real user. cart last, because it needs both.

That helped at the places where features met. Reviews only mean something once login exists. "Edit your own review" is meaningless without an author, so building accounts before reviews saved me from bolting ownership onto rows that never had it.

When I had a question I went to the Django docs first. They're good at explaining why something works the way it does, not just what to call. The pages on sessions and on the auth decorators answered most of my design questions. Where the docs gave a few valid options I picked whichever kept logic out of the templates. That's why the cart total is a helper function and the quantity lookup is a custom filter, instead of both being jammed into the page.

For bugs I used Django's debug traceback and the dev server's auto reload to keep the loop short, and checked the admin to see what was actually in the database instead of guessing.

The habit that helped most was not trusting the happy path. It's easy to test a feature by doing the exact thing it was built for. All my bugs were one step to the side. An empty review. Refreshing the confirmation page after checking out. Trying to edit a review that wasn't mine. Walking each screen through those is what turned the login_required decorators and ownership checks into something I could explain instead of something I copied.
