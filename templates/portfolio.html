GT Movies Store

An online report on GT Movies Store — a Django web application for browsing a movie catalog, reviewing titles, and placing orders. This page covers who I am, what I built, how the screens satisfy the project’s user stories, and how I actually worked through it.

02GT Movies Store

GT Movies Store is a full-stack Django application built around a movie storefront. A visitor can browse and search the catalog and read reviews without an account; once they sign up, they can write and manage their own reviews, build a cart, and check out into a persistent order history.

Architecture

Rather than one monolithic app, the project is split into four focused Django apps under a moviestore project, each owning its own URLs, views, templates, and models. The root URLconf mounts them at their own prefixes:

  • homeLanding page and About page — static marketing surface, no models.
  • moviesThe Movie and Review models, catalog listing, search, detail pages, and the full review lifecycle.
  • cartSession-backed cart plus the Order and Item models that a checkout writes to.
  • accountsSignup, login, logout, and per-user order history on top of Django’s built-in User.

The data model is deliberately small. Movie holds a name, price, description, and an uploaded image; Review foreign-keys to both a movie and a user, so a review always knows who wrote it — which is what makes ownership checks possible later. At checkout, an Order is created for the user and one Item row is written per movie, each snapshotting the price and quantity at purchase time. That snapshot matters: because the price is copied onto the item rather than read through the foreign key, editing a movie’s price later doesn’t silently rewrite the history of what someone already paid.

The cart itself lives in the Django session instead of the database, as a mapping of movie ID to quantity. An anonymous visitor can therefore fill a cart before having an account; only purchase is gated behind @login_required, so the login wall appears at checkout rather than at the door.

Screens and features against the user stories

Screen Route How it answers the user story
Home / Entry point with the store’s branding and a path into the catalog, so a first-time visitor lands somewhere oriented rather than on a bare list.
About /about Static informational page — “as a visitor I want to know what this store is.”
Movie list /movies/ “Browse all movies” and “search for a movie by name.” The view reads a search query parameter and filters with a case-insensitive name__icontains match; with no parameter it falls through to the full catalog, so the same screen serves both stories and an empty search never strands the user.
Movie detail /movies/<id>/ “See a movie’s details” and “read its reviews.” Renders the image, description, and price, pulls every Review for that movie, and hosts the add-to-cart quantity form and the review composer.
Sign up /accounts/signup “Create an account.” Wraps Django’s UserCreationForm in a custom subclass that strips the default help text and applies Bootstrap classes, with a custom error list that renders validation failures as styled alerts instead of a raw <ul>.
Login / logout /accounts/login/ “Log in and out.” Authenticates against Django’s backend and re-renders the form with a single non-enumerating error message on failure, so a wrong password doesn’t reveal whether the username exists.
Cart /cart/ “Add movies to a cart, with a quantity, and see the total.” Lists everything in the session cart, computes the running total in a dedicated calculate_cart_total helper, and offers a clear-cart action. A custom template filter, get_quantity, looks up each movie’s quantity from the session dictionary inside the template — Django templates can’t subscript a dict by variable key, so that filter is what keeps the logic out of the view.
Purchase confirmation /cart/purchase/ “Check out.” Persists the Order and its Item rows, empties the session cart so a refresh can’t double-order, and confirms with the new order ID.
Order history /accounts/orders/ “See my past orders.” Reads orders through the reverse relation on the logged-in user, so the query is scoped to that account by construction rather than by a filter someone could forget.
Create / edit / delete review /movies/<id>/review/… “Write a review, and edit or delete my own.” All four review views sit behind @login_required. Edit re-checks that the review’s author is the current user and redirects away if not, and delete scopes its lookup to user=request.user so someone else’s review 404s instead of being removed. Empty comments are rejected on both create and edit.
Report review /movies/<id>/review/<id>/report/ An addition beyond the core stories: a signed-in user can remove a review they consider inappropriate, giving the community a way to clear bad content without waiting on an admin.
Admin /admin/ Django’s admin, with the models registered so a staff user can manage the catalog — including poster uploads, which are written to media/movie_images/ and served through a MEDIA_URL static route in development.

Interface

Every screen extends one base.html template holding the navigation bar and footer, so a new page inherits the shared chrome for free. The nav is authentication-aware: it swaps Login and Sign Up for Orders and a Logout link labelled with the current username, which gives the user a persistent signal about which account they’re in. Layout is Bootstrap 5 over a small custom stylesheet, with a collapsing toggle so the store stays usable at phone width.

03Process

I worked through this incrementally, one Django app at a time, treating each user story as the unit of work. Rather than designing the whole schema up front and wiring views to it afterwards, I took a vertical slice per feature — model, URL, view, template — and confirmed it worked in the browser before moving to the next. The order followed the data dependencies: home first to get a project skeleton rendering, then movies since everything else refers to a movie, then accounts because reviews and orders both need a real user, and cart last as it depends on both.

That ordering paid off at the points where features met. Reviews, for instance, only became meaningful once authentication existed — a review needs an author before “edit your own review” means anything — so building accounts before the review lifecycle avoided retrofitting ownership onto anonymous rows.

For questions and doubts, my first stop was the official Django documentation, which is unusually good at explaining not just the API but the intent behind it; the reference on sessions and on the authentication decorators settled most of my design questions directly. Where the docs described several valid options, I picked the one that kept logic out of the templates — that’s how the cart total ended up in a helper function and the quantity lookup in a custom template filter rather than both being inlined into the page. When something behaved unexpectedly, I leaned on Django’s debug traceback and the development server’s auto-reload to shorten the loop, and checked my assumptions about what was actually in the database through the admin rather than guessing.

The most useful habit was distrusting the happy path. It’s easy to verify a feature by doing the thing it was built for; the bugs were all in the cases next door — submitting an empty review, refreshing the confirmation page after checking out, trying to edit a review belonging to someone else. Walking each screen through those cases is what turned the @login_required decorators and ownership checks from boilerplate into something I could explain.
